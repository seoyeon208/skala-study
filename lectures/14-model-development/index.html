01

데이터 분석은 프로세스다

기술 하나보다 단계 사이의 연결과 의사결정이 중요하다
▸
Business
누가 어떤 결정을 왜 내려야 하는지 정의
Data
분석 단위와 시점에 맞춰 수집·통합·품질 점검
Model
Baseline부터 검증하고 필요한 복잡도만 추가
Evaluation
업무 비용에 맞는 지표와 Threshold로 판단
Operation
예측 제공, Drift 감시, 재학습까지 책임

데이터 준비·전처리·Feature Engineering처럼 용어의 경계는 조직과 담당자에 따라 달라질 수 있습니다. 이름을 외우기보다 언제 어떤 데이터를 어떻게 바꾸고, 그 결과가 어느 단계에 사용되는지 설명할 수 있어야 합니다.

실무 관점

머신러닝과 딥러닝은 전체 프로세스에 들어가는 도구입니다. 통계 분석이나 명시적 Rule이 문제에 더 알맞다면 복잡한 모델을 억지로 사용할 필요가 없습니다.

완료 조건을 먼저 정한다

“AUC가 높다”로 끝내지 않습니다. 예측을 누가 사용하고 언제 행동하는지, 오탐과 미탐 중 무엇이 더 비싼지, 운영 데이터와 정답을 어떻게 다시 모을지까지 정합니다.

02

문제·Target·기간 설계

모집단·분석 단위·예측 시점이 모델의 의미를 결정
▸
설계 요소결정할 내용은행 이탈 예시
Population누구를 예측 대상에 포함할지기준일 현재 정상 개인 고객
Unit한 행이 무엇을 뜻하는지고객 1명 × 기준일 1개
TargetPositive Class의 업무 정의향후 6개월 안에 완전 이탈
Observation WindowFeature를 모을 과거 기간기준일 이전 3년 거래
Prediction WindowTarget을 관찰할 미래 기간기준일 이후 6개월
Reference Date과거와 미래를 나누는 기준월말 스코어링 기준일
과거 Feature 구간 ── 기준일 ── 미래 Target 구간
       3년          예측 시점          6개월

Target 정의가 달라지면 같은 데이터라도 완전히 다른 모델이 됩니다. “이탈”이 잔액 0인지, 계좌 해지인지, 일정 기간 미활동인지 업무 담당자와 먼저 합의합니다.

시간 누수 방지

기준일 이후에 생긴 상담 결과나 해지 처리 코드는 예측 시점에 알 수 없으므로 Feature로 사용할 수 없습니다. 관찰 기간과 예측 기간을 분리하는 이유입니다.

03

데이터 준비·품질·EDA

모델보다 오래 걸리고 결과의 상한을 정하는 단계
▸
점검질문은행 이탈 예시
Schema타입·단위·범주 정의가 맞는가?기준일과 계좌개설일을 날짜형으로 변환
Completeness결측 비율과 발생 방식은?연봉 결측이 특정 채널에 몰렸는지 확인
Validity불가능한 값이 있는가?음수 잔액·0세·미래 개설일 탐지
Consistency출처별 코드와 의미가 같은가?국가명·성별 표기 통일
Timeliness예측 시점에 실제 이용 가능한가?이탈 후 생성된 정보는 제외
Uniqueness분석 단위가 중복되지 않는가?고객 1명당 기준일 1행인지 확인

EDA는 예쁜 그래프를 만드는 단계가 아닙니다. 분포·범주 비율·결측·이상치와 Target 비율을 확인해 데이터 설계 오류와 모델 위험을 찾습니다. 데이터 품질이 나쁘면 어떤 알고리즘도 안정적인 성능을 만들기 어렵습니다.

확인 순서

shape → head → info → describe → 범주 빈도 → Target 비율 순으로 구조를 파악합니다. 숫자형으로 저장된 ID나 0/1 범주처럼 dtype만으로 의미를 단정하지 않습니다.

04

Feature Engineering

Creation·Transformation·Selection의 목적을 구분
▸
구분목적예시
Creation원본에서 더 설명력 있는 변수 생성기준일 - 계좌개설일 = 가입기간
Transformation학습하기 좋은 분포·단위·표현으로 변환결측 대체, 로그, Scaling, One-Hot Encoding
Selection무의미·중복·불안정한 Feature 제거단일값, 높은 상관, 낮은 Importance 제거
Extraction여러 변수를 새로운 축으로 압축PCA, 임베딩

행 하나만으로 계산하는 가입기간은 분할 전 만들어도 다른 행의 정보를 보지 않습니다. 반면 전체 평균·빈도·Target을 이용하는 변환은 Train으로만 학습해야 합니다. “Feature Creation은 항상 분할 전”처럼 순서를 외우면 누수가 생깁니다.

Selection의 네 단계

도메인·법적 사용 가능성 → 데이터 신뢰성 → 중복성 → Target 설명력을 순서대로 봅니다. 중요도가 낮아도 규제·안정성·비용 측면에서 의미가 있을 수 있어 자동 삭제만 믿지 않습니다.

PCA 주의

차원의 저주와 다중공선성을 줄일 수 있지만 원래 Feature 의미가 섞여 개별 변수 해석이 어려워집니다. 예측 성능과 해석 가능성의 교환관계를 확인합니다.

05

분할과 Leakage

미래 데이터처럼 행동하는 평가 환경 만들기
▸
분할언제 쓰나주의점
Random행들이 독립이고 시간 순서가 중요하지 않을 때클래스 비율이 작은 데이터는 흔들릴 수 있음
Stratified분류 Target 비율을 각 세트에 유지할 때시간·고객 그룹 문제는 해결하지 못함
Group한 고객·환자·장비가 여러 행일 때같은 그룹이 Train과 Test에 함께 들어가면 안 됨
Time-based미래를 예측하는 시계열·운영 모델과거로 학습하고 그 이후 기간으로 검증
Train
모델과 전처리 통계가 실제로 학습하는 데이터
Validation
모델·Hyperparameter·Threshold를 선택하는 데이터
Test
모든 선택이 끝난 뒤 일반화 성능을 한 번 확인하는 데이터

누수의 네 가지 형태

종류예막는 방법
Target Leakage이탈 처리 결과를 Feature로 사용예측 시점에 알 수 있는 변수만 사용
Train–Test Contamination전체 데이터 평균으로 결측 대체전처리는 Train에 fit, 나머지는 transform
Time Leakage미래 거래로 과거 이탈을 예측기준일과 시간 순서를 명시
Group Leakage같은 고객의 행이 양쪽에 존재Group 단위로 분할
Pipeline 원칙

결측 대체·Scaling·Encoding·Sampling을 모델과 하나의 Pipeline으로 묶으면 각 Fold의 Train에서만 fit되어 누수를 줄일 수 있습니다. Sampling은 검증·Test가 아니라 Train Fold 내부에서만 수행합니다.

06

Baseline·불균형

복잡한 모델 전에 비교 기준부터 세운다
▸

Baseline은 “현재 방식보다 모델이 실제로 나은가?”를 판단하는 최소 기준입니다. 분류에서는 최빈 클래스만 예측하는 Dummy 모델, 회귀에서는 평균·중앙값 예측, 업무에서는 기존 Rule이 기준이 될 수 있습니다.

Accuracy 함정

이탈 고객이 5%라면 모두 비이탈이라고 예측해도 Accuracy는 95%입니다. 하지만 이탈 고객을 한 명도 찾지 못하므로 Recall은 0입니다.

방법장점주의점
Class Weight데이터를 복제하지 않고 소수 클래스 손실을 키움확률 보정과 Threshold를 다시 확인
Under-sampling빠르고 데이터 크기를 줄임다수 클래스 정보 손실
Over-sampling / SMOTE소수 클래스 학습 신호 강화Train Fold 내부에서만 수행, 합성값 타당성 확인
Threshold 조정재학습 없이 Precision–Recall 균형 변경업무 비용과 처리 용량 기준 필요

불균형 해결은 데이터 비율을 50:50으로 만드는 일이 아닙니다. 실제 업무 비용을 반영한 지표와 Threshold에서 쓸 만한 모델을 만드는 일입니다.

07

Validation·Cross Validation

한 번의 우연한 분할에 결론을 맡기지 않는다
▸
방법적합한 상황핵심
KFold일반 회귀·균형 분류K번 학습해 평균과 편차 확인
StratifiedKFold불균형 분류각 Fold의 클래스 비율 유지
GroupKFold동일 개체의 반복 관측그룹 간 독립성 보존
TimeSeriesSplit시간 순서가 있는 예측항상 과거로 학습해 미래 검증

Cross Validation의 평균은 기대 성능, Fold 간 편차는 안정성을 보여 줍니다. 평균만 높고 편차가 크면 표본이나 시기에 민감한 모델일 수 있습니다.

Test는 마지막에 한 번

Validation 결과로 모델을 선택하고 Test를 반복 확인하면 Test도 사실상 Validation이 됩니다. 종합실습에서 Validation과 Test 평균 AUC를 비교하는 것은 학습용 규칙이며, 실제 프로젝트에서는 Test를 최종 독립 평가로 남깁니다.

08

Hyperparameter 최적화

탐색 공간·검증 전략·비용을 함께 설계
▸

Parameter는 학습으로 얻는 가중치이고, Hyperparameter는 학습 전에 정하는 나무 깊이·개수·학습률 같은 설정입니다.

탐색법특징언제 유용한가
Grid Search지정 조합을 모두 시도후보가 적고 범위가 좁을 때
Random Search분포에서 무작위 조합을 시도변수가 많고 빠르게 넓게 볼 때
Bayesian Optimization이전 결과로 다음 유망 지점 선택한 번의 학습 비용이 큰 경우
Underfitting
Train과 Validation 모두 낮음 → Feature·모델 용량·학습 방식을 개선
Overfitting
Train은 높고 Validation은 낮음 → 규제·단순화·데이터·검증을 점검
최적화 순서

Metric과 CV를 먼저 고정하고, 기본 모델 → 넓은 Random/Bayesian 탐색 → 좁은 범위 재탐색 순으로 진행합니다. 잘못된 분할이나 누수를 Hyperparameter로 고칠 수는 없습니다.

09

분류 평가지표

정답 개수보다 오류의 종류와 비용을 본다
▸
실제 \ 예측PositiveNegative
PositiveTP: 이탈을 이탈로FN: 이탈을 비이탈로
NegativeFP: 비이탈을 이탈로TN: 비이탈을 비이탈로
지표식의미
Accuracy(TP+TN) / 전체전체 중 맞춘 비율. 불균형에서 과신 주의
PrecisionTP / (TP+FP)이탈이라고 한 고객 중 실제 이탈 비율
RecallTP / (TP+FN)실제 이탈 고객 중 찾아낸 비율
F12PR / (P+R)Precision과 Recall의 조화 평균
SpecificityTN / (TN+FP)실제 비이탈을 제대로 거른 비율
업무 비용으로 선택

놓친 이탈 고객의 손실이 크면 Recall을, 연락 비용·민원이 크면 Precision을 더 중시합니다. F1도 두 오류의 비용이 비슷하다는 암묵적 가정이 있으므로 만능 지표는 아닙니다.

10

AUC·Lift·Threshold

순위 성능과 실제 행동 기준을 분리해서 이해
▸
개념답하는 질문주의점
ROC-AUC임의의 Positive가 Negative보다 높은 점수를 받을 가능성은?Threshold와 실제 확률 정확도를 말하지 않음
PR-AUCPositive를 찾을 때 Precision–Recall 품질은?클래스 비율에 영향을 받으므로 같은 모집단끼리 비교
Lift상위 점수 고객을 선택하면 무작위보다 몇 배 잘 찾나?마케팅 대상 수·구간과 함께 제시
Calibration예측 0.8인 집단이 실제로 약 80% 발생하나?좋은 AUC와 좋은 확률 보정은 별개

Threshold는 확률을 최종 클래스나 행동으로 바꾸는 기준입니다. 낮추면 대체로 Recall이 오르고 FP도 늘며, 높이면 Precision이 오를 수 있지만 FN이 늘 수 있습니다.

기대 비용 = FN 수 × 놓친 이탈 비용 + FP 수 × 불필요 연락 비용
운영 제약 = 하루 상담 가능한 고객 수, 예산, 규제
모델 선택과 운영 선택

AUC는 모델의 순위 품질을 비교하고, Threshold는 비용·처리 용량에 맞춰 정합니다. “AUC가 높으니 0.5를 쓰자”는 결론은 성립하지 않습니다.

11

회귀 평가지표

오차 단위·이상치·0값 특성을 보고 고른다
▸
지표특징주의점
MAE절대 오차 평균, 원래 단위큰 오차를 MSE보다 덜 강하게 벌점
MSE제곱 오차 평균큰 오차에 민감하고 단위가 제곱됨
RMSEMSE의 제곱근, 원래 단위이상치 영향이 큼
MAPE백분율이라 해석이 쉬움실제값 0에서 정의되지 않고 작은 값에 폭발
R²평균 예측 대비 설명력음수도 가능하며 인과·좋은 운영 성능을 뜻하지 않음
지표도 Target 설계의 일부

매출처럼 큰 오차가 특히 치명적이면 RMSE, 이상치가 많고 대표적인 절대 오차가 중요하면 MAE를 우선 검토합니다. 서로 다른 Target 규모를 비교하려고 MAPE를 쓸 때는 0과 작은 실제값을 반드시 점검합니다.

12

Feature Importance·SHAP

무엇을 참고했는지와 어떻게 영향을 줬는지 구분
▸
도구보여 주는 것해석 질문
Tree Feature Importance분할에 기여한 전역 중요도모델이 자주·유용하게 쓴 변수는?
SHAP Importance평균 절대 SHAP 값전체적으로 영향이 큰 변수는?
SHAP Summary크기·방향·분포값이 클수록 예측을 어느 방향으로 미나?
Dependence한 변수 값과 영향의 관계비선형·상호작용 패턴이 있는가?
Force / Waterfall한 건의 기준값부터 예측까지 기여이 고객의 점수가 왜 이렇게 나왔나?

Tree Importance는 고유값이 많거나 상관된 변수에서 편향될 수 있습니다. SHAP도 상관된 Feature 사이에서 기여가 나뉠 수 있고, 결과는 모델의 예측 설명이지 원인 증명이 아닙니다.

안전한 해석 문장

“잔액이 이탈을 일으켰다”가 아니라 “이 모델은 다른 조건이 주어졌을 때 높은 잔액을 더 높은 이탈 점수와 연관해 사용했다”고 표현합니다.

AI가 만든 코드는 데이터 컬럼, 라이브러리 버전, 모델의 predict_proba 지원, Leakage, 지표 계산 대상을 직접 검토합니다. 먼저 분석 결정을 적고 AI에는 구현·반복 작업을 맡기는 편이 안전합니다.

Review map

자주 헷갈리는 포인트

Validation vs Test

Validation은 선택에 사용하고 Test는 선택이 끝난 뒤 최종 확인에만 사용합니다.

Feature 생성 시점

행 하나만 쓰는 계산은 미리 가능하지만 평균·범주·Target 통계는 Train에만 fit합니다.

AUC vs Threshold

AUC는 순위 품질, Threshold는 실제 행동과 오류 비용을 정합니다.

Importance vs Causality

모델이 사용한 관계를 설명할 뿐, 변수가 결과의 원인임을 증명하지 않습니다.

Data Drift vs Concept Drift

입력 분포 변화와 입력–정답 관계 변화는 다르며 대응도 다를 수 있습니다.

좋은 CV vs 좋은 운영

오프라인 성능 외에 Calibration, Latency, 안정성, 비용, 공정성을 봐야 합니다.

재학습 vs 재설계

최근 데이터만 필요하면 재학습, 관계나 문제 정의가 변했으면 재설계합니다.

모델 저장 vs 시스템 저장

전처리·Schema·버전·Threshold까지 함께 있어야 같은 예측을 재현할 수 있습니다.
