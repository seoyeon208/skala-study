01

컨테이너의 이해

VM과 무엇이 다른가 · 뒤에서 계속 쓸 다섯 낱말
▸

핵심 요지

VM은 물리 서버를 가상화 OS 단위로 나누고, 컨테이너는 호스트 커널을 공유하는 프로세스로 나눕니다. OS를 새로 얹지 않기 때문에 가볍고, 뜨는 속도가 빠르고, 같은 서버에 더 많이 올릴 수 있습니다.

구조 한눈에 비교

🖥️ 가상 서버 (VM)
  • APP + Bins/Libs + Guest OS 통째로
  • Hypervisor 위에서 동작
  • 이기종 OS 사용 가능
  • 부팅 수십 초 ~ 수 분
  • 물리 서버당 4~6개
VS
📦 컨테이너
  • APP + Bins/Libs 중심, 독립 커널은 없음
  • 호스트 커널을 그대로 공유
  • Host OS와 같은 계열만 가능
  • 부팅 수 초 ~ 수십 초
  • 물리 서버당 20~30개
정확히 이해하기

“컨테이너 안에는 OS가 없다”보다 “별도 커널이 없고 호스트 커널을 공유한다”가 정확합니다. Mac이나 Windows에서 Linux 컨테이너를 실행할 때 Docker Desktop은 내부의 가벼운 Linux VM을 이용합니다.

같이 나오는 개념: 레이어 · 빌드 캐시 · 멀티스테이지

  • 이미지는 한 덩어리가 아니라 여러 장이 쌓인 것입니다. 보통 RUN·COPY·ADD처럼 파일시스템을 바꾸는 명령이 레이어를 만들고, CMD·ENV·EXPOSE 같은 설정 명령은 이미지 메타데이터를 바꿉니다.
  • 빌드 캐시: 도커는 Dockerfile 명령을 줄 단위로 실행하고 결과를 저장해 둡니다. 같은 줄과 그 줄이 쓰는 파일이 그대로면 저장된 결과를 재사용 → 재빌드가 빨라짐.
  • 멀티스테이지 빌드: 빌드에 필요한 것과 실행에 필요한 것을 분리해서 최종 이미지 크기를 줄이는 기법.

컨테이너 생명주기

생성 → 실행 → 정지 → 삭제. 이 상태를 구분하지 못하면 "왜 안 뜨지?"에서 자주 막힙니다.

복습 포인트

이미지·컨테이너·레지스트리·볼륨·포트·레이어 여섯 개를 한 문장씩 설명할 수 있는지 확인하세요. Docker Desktop을 쓴다면 docker version에서 Client와 Server가 모두 연결되는지도 점검합니다.

헷갈리기 쉬운 부분
  • VM은 하이퍼바이저 위에 OS를 통째로 올리지만, 컨테이너는 호스트 커널을 그대로 공유하는 프로세스일 뿐이라는 차이를 "그냥 가벼운 VM"으로 오해하기 쉽습니다. 컨테이너는 VM의 축소판이 아니라 격리된 프로세스입니다.
  • EXPOSE와 포트 열기(-p)를 혼동하기 쉬운데, 이건 3장에서 다시 명확히 나옵니다.
02

나의 데이터베이스 만들기

설치 없이 이미지 이름 하나로 DB 띄우기 · 볼륨의 진짜 의미
▸

핵심 요지

"설치"라고 부를 만한 과정 없이, docker run 한 번으로 MariaDB가 뜹니다. 이 장의 진짜 요점은 "컨테이너를 지우면 내 데이터는 어떻게 되는가"입니다.

핵심 명령 흐름

docker run -d --name mariadb \
  -e MYSQL_ROOT_PASSWORD=password123 \
  -e MYSQL_DATABASE=skala \
  -p 3306:3306 \
  mariadb:latest

docker exec -it mariadb mariadb -u root -p   # 컨테이너 안 SQL 실행

익명 볼륨 vs 이름 붙인(named) 볼륨

  • mariadb 이미지는 /var/lib/mysql에 익명 볼륨을 자동으로 붙입니다.
  • 일반적인 docker rm만으로 익명 볼륨이 자동 삭제되는 것은 아닙니다. 다만 새 컨테이너에는 새 익명 볼륨이 붙기 때문에 이전 데이터와 연결이 끊겨 사라진 것처럼 보입니다.
  • 데이터를 남기려면 -v mariadb-data:/var/lib/mysql처럼 이름을 붙인 볼륨을 직접 지정해야 합니다.
# 이름 붙인 볼륨으로 데이터 남기기
docker run -d --name mariadb \
  -e MYSQL_ROOT_PASSWORD=password123 \
  -v mariadb-data:/var/lib/mysql \
  mariadb:latest
삭제 조건을 정확히 구분

docker rm -v 컨테이너명은 연결된 익명 볼륨까지 지우며, docker run --rm으로 실행한 컨테이너는 종료 시 익명 볼륨도 함께 정리될 수 있습니다. 네임드 볼륨은 다시 연결하기 쉽고 명시적으로 삭제하기 전까지 유지되므로 데이터 저장에는 네임드 볼륨을 기본으로 생각하세요.

정리 명령

명령하는 일
docker volume prune어느 컨테이너에도 안 쓰이는 익명 볼륨 정리
docker image prune -a컨테이너에 안 붙은 이미지 전부 삭제
docker system prune -a컨테이너/네트워크/이미지/빌드캐시 전부 정리
복습 포인트

VSCode의 Database 확장이나 DBeaver로 접속해, 컨테이너를 재생성한 뒤에도 네임드 볼륨의 데이터가 남는지 직접 확인합니다.

헷갈리기 쉬운 부분

"-v 옵션을 안 줬다고 데이터가 아예 저장 안 되는 것"이 아닙니다. MariaDB 이미지가 익명 볼륨을 만들지만, 새 컨테이너가 그 볼륨을 자동으로 다시 선택하지 않습니다. 핵심은 삭제 여부보다 다시 식별하고 연결할 수 있는가이며, 그래서 네임드 볼륨을 사용합니다.

03

웹 서비스 실행 컨테이너 만들기

v1.0 껍데기 → v1.1 코드 내장 → v1.2 자동 실행, 3단계 진화
▸

핵심 요지

같은 웹앱을 세 버전으로 띄우며 "코드를 어디에 두는가"와 "누가 실행하는가"가 컨테이너를 서비스로 만드는 두 가지 핵심 요소임을 보여줍니다.

버전webserver.py 위치포트실행 주체재시작하면
v1.0호스트 (-v 마운트)안 엶사람이 exec해서직접 다시 띄워야 함
v1.1이미지 안 (COPY)-p 8888:8080사람이 exec해서직접 다시 띄워야 함
v1.2이미지 안-p 8888:8080CMD로 컨테이너가 스스로알아서 돌아옴

왜 -p 가 필요한가 (자주 나오는 질문)

컨테이너 안에서는 curl localhost:8080이 되지만, 밖(내 PC)에서는 -p 8888:8080으로 길을 뚫어야만 접속됩니다.

내 pclocalhost:8888
⇄
-p 8888:8080이 뚫어 준 길
⇄
컨테이너0.0.0.0:8080

Dockerfile의 EXPOSE는 "이 포트를 씁니다"라는 표시(문서화)일 뿐, 실제로 길을 여는 것은 docker run -p입니다.

복습 포인트

host="0.0.0.0"은 모든 인터페이스에서 요청을 받지만, 127.0.0.1은 컨테이너 내부 loopback에만 묶입니다. 이 차이를 -p와 함께 설명해보세요.

헷갈리기 쉬운 부분
  • v1.2가 항상 정답은 아닙니다. 개발 중에는 v1.0처럼 -v로 코드를 붙여 두는 편이 코드 수정 즉시 반영되어 더 빠릅니다. 배포할 때는 이미지 하나로 어디서든 같은 서비스가 뜨는 v1.2가 맞습니다.
  • 익명 볼륨과 네임드 볼륨의 차이: 익명 볼륨도 일반 삭제 후 남을 수 있지만 이름이 없어 재연결이 어렵습니다. 네임드 볼륨은 명시적으로 다시 연결하기 쉽습니다. (2장 내용과 이어짐)
04

컨테이너 이미지 구조

이미지를 tar로 직접 풀어서 눈으로 확인
▸

핵심 요지

이미지는 특별한 파일 형식이 아니라, tar 묶음 여러 개 + 그것을 어떤 순서로 쌓을지 적은 JSON이 전부입니다.

docker save -o linux.tar container-linux:1.0
tar xf linux.tar
# 결과: index.json, manifest.json, oci-layout, blobs/sha256/
manifest.json
Config + Layers 목록 — 순서 = 쌓인 순서
index.json
어떤 매니페스트를 볼지 가리키는 목차
oci-layout
이 디렉터리가 OCI 이미지 레이아웃이라는 표시
blobs/sha256/
레이어 tar + 설정 JSON — 이름 = 내용의 해시

docker history — 레이어를 Dockerfile 줄 단위로 보기

docker history는 레이어를 해시가 아니라 "Dockerfile의 어느 줄이 만들었는지"로 보여줍니다. CMD·VOLUME처럼 파일을 만들지 않는 명령은 레이어 크기가 0B입니다.

레이어는 이미지끼리 공유된다

v1.0레이어 7개
→
v1.1 (+COPY)레이어 8개
→
v1.2 (CMD만 변경)동일 8개

이름이 내용의 해시라는 사실 하나로 빌드 캐시 재사용, push 시 레이어 재사용, pull 시 레이어 공유가 전부 설명됩니다.

복습 포인트

docker save → tar xf → cat manifest.json | jq 순서로 이미지가 레이어와 메타데이터의 묶음이라는 사실을 직접 확인합니다.

헷갈리기 쉬운 부분

이미지를 "통째로 하나의 파일"로 생각하면 캐시 재사용이나 push 재사용이 이해되지 않습니다. 반드시 "레이어 여러 장 + 그 목록(manifest)"이라는 구조로 기억해야 8장(Dockerfile)과 9장(Registry)이 자연스럽게 이어집니다.

핵심 요지

컨테이너 = 격리된 프로세스. 무엇으로 격리하는지 네 가지 기술과, 누가 그 일을 하는지 실행 체인을 다룹니다.

실행 체인 한눈에

docker cli

namespace — "보이는 것"을 나눈다

PID

컨테이너마다 별도 프로세스 테이블. 다른 컨테이너 프로세스 접근 불가

Network

네트워크 디바이스·IP·포트·라우팅 테이블을 namespace별로 할당

UID/GID

사용자/그룹 ID 공간 격리

Mount

컨테이너마다 특정 디렉토리를 루트 파일시스템(rootfs)으로 보이게 함

UTS

독자적인 호스트명·도메인명

IPC

공유메모리·큐·세마포어 등 프로세스 간 통신 자원 분리

cgroup — "쓸 수 있는 양"을 나눈다

CPU, 메모리, 디스크 I/O 같은 자원을 그룹별로 제한합니다. 메모리 초과 시 OOM Killer가 프로세스를 강제 종료합니다.

docker run --rm --memory 300m alpine cat /sys/fs/cgroup/memory.max
314572800   # 300 x 1024 x 1024

docker run --rm --cpus 0.5 alpine cat /sys/fs/cgroup/cpu.max
50000 100000   # 100ms 중 50ms만 사용 가능

이미지는 왜 겹쳐 쌓는가 — 층은 두 가지뿐

쓰기 층
컨테이너가 만들거나 고친 파일이 쌓임 · 컨테이너마다 하나씩 · Copy on Write
읽기 전용 층 C
이미지 레이어. 절대 바뀌지 않음
읽기 전용 층 B
이미지 레이어. 절대 바뀌지 않음
읽기 전용 층 A
이미지 레이어. 절대 바뀌지 않음

같은 이름의 파일이 양쪽에 있으면 쓰기 층 것이 이깁니다. 컨테이너를 지우면 쓰기 층만 사라지고 이미지 층은 남습니다.

네트워크 — bridge부터 overlay까지

기본 bridge에서는 컨테이너의 eth0가 호스트의 veth와 연결되고, docker0가 스위치처럼 컨테이너 사이를 중계합니다. -p로 공개한 포트의 주소·포트 변환은 iptables 또는 nftables 규칙이 담당합니다.

외부 요청 → host:8080 → iptables/NAT → containerIP:80
컨테이너 eth0 ↔ veth ↔ docker0 bridge
유형설명통신 범위
bridge단일 Docker 호스트 내 기본 네트워크한 호스트 내 컨테이너끼리
host컨테이너가 호스트의 IP 그대로 사용호스트 공유
none외부 네트워크를 연결하지 않음loopback만 사용
overlay여러 Docker 호스트 간 네트워크다중 호스트 가능
복습 포인트

docker run --rm alpine ls -l /proc/1/ns로 namespace를 확인하고, namespace는 보이는 범위·cgroup은 사용량이라는 차이를 말로 설명해보세요.

헷갈리기 쉬운 부분
  • namespace와 cgroup의 역할 구분: namespace는 "무엇이 보이는가"(격리), cgroup은 "얼마나 쓸 수 있는가"(제한)입니다. 흔히 둘 다 "격리 기술"로 뭉뚱그려 외우는데, 시험/실습에서 구분해서 물어보면 헷갈립니다.
  • LXC vs runc: LXC(구식, namespace+cgroup 직접 제어)가 경량화된 runc로 대체되었습니다. runc가 LXC의 후속 개념입니다.
  • runc와 컨테이너 프로세스의 부모-자식 관계 변화: runc(자식) → init process(손자)였다가, runc 종료 후 init process의 부모가 shim으로 바뀝니다. 이 순서를 거꾸로 외우기 쉽습니다.

컨테이너 플랫폼

Docker · Podman · containerd · CRI-O · Kaniko, 층이 다른 도구들
▸

핵심 요지

도커 하나가 다 하던 일이 여러 도구로 나뉘었습니다. 이름은 많아 보이지만 "사람이 쓰는 도구" vs "그 아래 런타임" vs "맨 아래"로 층이 다릅니다.

사람이 쓰는 도구
Docker (CLI+데몬+빌드, 개발자 PC) · Podman (데몬리스, 보안↑)
런타임 레이어
containerd (이미지·수명주기, 쿠버네티스 기본) · CRI-O (K8s 전용 경량, OpenShift)
맨 아래
runc — namespace·cgroup을 실제로 만드는 최하위 도구
CI 전용
Kaniko — 데몬 없이 클러스터 안에서 이미지 빌드 (Tekton 등)

쿠버네티스는 CRI(Container Runtime Interface) 규격만 맞으면 되므로 Docker 엔진 전체가 필요 없습니다. 실행 흐름은 5장과 같습니다: kubelet → CRI → containerd → shim → runc.

복습 포인트

실습 중 docker version과 docker info로 내 PC의 실제 구성 요소(Engine/containerd/runc 버전)를 확인하는 부분이 있습니다. 어느 것으로 이미지를 만들든 결과물은 같은 OCI 표준 이미지라는 점이 9장(Harbor push)으로 이어집니다.

헷갈리기 쉬운 부분

"Docker와 containerd가 경쟁 관계"라고 오해하기 쉽지만, 사실 containerd는 Docker 내부에서 쓰이는 구성요소이자 동시에 독립적으로도 쓰일 수 있는 CNCF 프로젝트입니다. Docker가 containerd를 포함하는 상위 도구입니다.

핵심 요지

2일차 집중실습 1·2가 이 장 기반입니다. 이미지를 찾고, 받고, 띄우고, 들여다보고, 치우는 명령을 하나씩 손으로 익히는 장입니다.

명령어 한눈에

명령하는 일
docker search / pull이미지를 찾고 내려받는다
docker images / rmi이미지 목록을 보고, 지운다

이미지 레이어와 스토리지

이미지 A를 지워도 이미지 B가 같은 레이어(A, B, C)를 쓰고 있으면 그 레이어는 지워지지 않습니다. 이미 존재하는 레이어는 새로 받을 필요가 없다는 원리는 4장의 레이어 공유 개념과 동일합니다.

복습 포인트

docker run은 새 컨테이너를 만들고, docker exec은 실행 중인 컨테이너 안에서 새 프로세스를 실행합니다. 종료된 컨테이너까지 보려면 docker ps -a를 사용합니다.

헷갈리기 쉬운 부분
  • run은 "만들어서 띄운다", start는 "이미 있는 것을 켠다"입니다. 이 둘을 헷갈리면 run을 반복 실행해서 같은 이름의 컨테이너가 계속 쌓입니다.
  • exec는 컨테이너가 떠 있을 때만 동작합니다. 멈춘 컨테이너에는 먼저 start를 해야 합니다.

Dockerfile 작성

뼈대(FROM·WORKDIR·USER) · 내용(COPY·RUN·ENV) · 실행(CMD·ENTRYPOINT)
▸

핵심 요지

Dockerfile은 "무엇을 이미지에 넣을지"를 위에서부터 적어 둔 텍스트 파일입니다. 2일차 집중실습 3·4가 이 장 기반입니다.

Dockerfile 명령어 총정리

키워드설명
FROMbase 이미지 지정. 반드시 파일 맨 앞 (ARG 제외)
WORKDIR이후 명령이 실행될 디렉터리 (cd 대신 사용)
RUN빌드 중 실행할 명령. 실행할 때마다 레이어 생성
COPY로컬 파일/디렉토리 복사 전용
ADDCOPY 기능 + URL 다운로드 + 압축 자동 해제
ENV실행되는 앱·프로세스에 환경변수 설정
LABEL메타 정보. 실행에 영향 없음
EXPOSE쓰는 포트를 문서화 (실제로 여는 건 아님)
USER이후 RUN/CMD/ENTRYPOINT를 실행할 사용자 지정
VOLUME호스트와 공유할 디렉터리 표시
CMD컨테이너 시작 시 실행할 기본값 (덮어쓰기 가능)
ENTRYPOINT컨테이너 시작 시 실행할 고정 명령

ADD vs COPY

웬만하면 COPY를 씁니다. ADD는 URL 다운로드나 압축 해제가 필요할 때만 씁니다 — 의도가 명확하지 않은 ADD는 예상치 못한 압축 해제를 유발할 수 있습니다.

CMD vs ENTRYPOINT — 실제 동작으로 비교

🔒 ENTRYPOINT — 고정
  • docker run 뒤 인자는 뒤에 이어 붙는다
  • 컨테이너의 실행 목적을 고정할 때 사용
  • 여러 개면 마지막 것만 유효
VS
⚙️ CMD — 기본값
  • docker run 뒤 인자는 통째로 대체
  • 기본 실행 명령을 지정할 때 사용
  • 여러 개면 마지막 것만 유효
# 1) ENTRYPOINT만 있을 때 — ENTRYPOINT ["echo", "This"]
docker run demo-e               → This
docker run demo-e hello world   → This hello world   # 뒤에 붙는다

# 2) CMD만 있을 때 — CMD ["echo", "This is the default command"]
docker run demo-c            → This is the default command
docker run demo-c echo bye   → bye                   # 통째로 바뀐다

# 3) 둘 다 있을 때
# ENTRYPOINT ["echo", "This"]
# CMD ["is", "the", "default", "command"]
docker run demo-ec         → This is the default command
docker run demo-ec hello   → This hello               # CMD 부분만 바뀐다

ENTRYPOINT는 고정, CMD는 기본값(=인자). docker run 뒤에 준 인자는 항상 CMD 자리를 대신합니다.

멀티스테이지 FROM 예시

FROM node:18-alpine AS frontend-builder
...
FROM golang:1.21-alpine AS backend-builder
...
COPY --from=frontend-builder /frontend/dist /app/public
COPY --from=backend-builder /backend/server /app/server

순서가 빌드 시간을 정한다 (캐시 최적화)

# 나쁜 순서 — 소스를 먼저 복사 (소스 바뀌면 캐시 깨짐)
COPY . .
RUN pip install --no-cache-dir -r requirements.txt

# 좋은 순서 — 잘 안 바뀌는 것을 먼저
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .                     # 소스는 맨 뒤에

실측 결과: 한 줄만 고친 재빌드 기준 나쁜 순서 3.97초 vs 좋은 순서 0.57초 — 약 7배 차이.

실무 빌드·보안 체크리스트

  • .dockerignore에 .git, node_modules, 빌드 산출물과 .env를 제외해 컨텍스트와 노출 범위를 줄입니다.
  • 운영 이미지는 latest만 믿지 말고 검증한 버전 태그나 digest로 고정해 재현성을 높입니다.
  • 필요한 사용자와 권한을 만든 뒤 USER로 전환해 애플리케이션을 non-root로 실행합니다.
  • 토큰·비밀번호 같은 비밀값을 Dockerfile의 ARG나 ENV에 넣지 않습니다. 런타임 secret 기능이나 배포 환경의 비밀 관리 도구로 주입합니다.
  • 멀티스테이지 빌드로 컴파일러와 패키지 캐시를 최종 이미지에서 제외하고, 배포 전 취약점 스캔을 수행합니다.
복습 포인트

Multi-stage Build는 여러 OS를 동시에 실행하는 기능이 아닙니다. 빌드 도구는 builder 단계에 남기고 실행 파일과 런타임만 최종 단계로 복사해 이미지 크기와 공격 표면을 줄이는 방식입니다.

헷갈리기 쉬운 부분
  • Dockerfile에 CMD나 ENTRYPOINT가 여러 개 있으면 마지막 것만 유효합니다. (레이어가 여러 겹 쌓이는 것과 다름)
  • docker run my-image "Override CMD"처럼 문자열 통째로 넘기면 셸 명령이 아니라 실행 파일로 해석되어 "executable file not found" 오류가 날 수 있습니다. sh -c "..." 형태로 감싸야 할 때가 있습니다.
  • EXPOSE는 문서일 뿐이라는 점(3장과 연결). 실제 포트를 여는 것은 항상 docker run -p입니다.

Registry Push 실습

Harbor에 로그인 → tag → push → pull, 이미지 이름이 곧 주소
▸

핵심 요지

내 PC에서 만든 이미지를 다른 PC나 쿠버네티스에서 쓰려면 레지스트리에 올려야 합니다. 이 과정은 Harbor(광주 캠퍼스 전용 Private Registry)를 사용합니다.

이미지 이름의 구조 — 이름이 곧 주소

harbor.skala-gj.com/skala-gj1/skala-webserver:1.0.0
^레지스트리 주소      ^프로젝트(계정)  ^이미지 이름    ^태그

레지스트리 주소가 없으면 도커는 자동으로 Docker Hub로 보냅니다. 프로젝트 이름은 로그인한 계정과 같아야 push가 됩니다.

4단계 흐름

1login
→
2tag
→
3push
→
4pull & run
docker login harbor.skala-gj.com -u skala-gj1
docker tag skala-webserver:1.0.0 harbor.skala-gj.com/skala-gj1/skala-webserver:1.0.0
docker push harbor.skala-gj.com/skala-gj1/skala-webserver:1.0.0
docker pull harbor.skala-gj.com/skala-gj1/skala-webserver:1.0.0   # 다른 곳에서

docker tag는 이미지를 복사하는 게 아니라 이름표를 하나 더 다는 것입니다 (IMAGE ID가 동일).

두 번째 push — 레이어 재사용 확인

파일 하나만 고쳐 1.0.1로 다시 push하면, nginx 베이스 레이어들은 Layer already exists로 표시되고 바뀐 레이어만 오갑니다. (4장 레이어 공유, 8장 캐시 순서 최적화가 여기서 값을 발휘)

자주 나는 오류 3가지

오류 상황원인/해결
push access denied레지스트리 주소를 빼고 push함 → tag를 harbor 주소로 다시 붙이기
권한 오류프로젝트 이름이 로그인 계정과 다름 → tag의 프로젝트명을 계정과 일치시키기
인증 실패로그인이 풀림 → docker login 재실행
복습 포인트

docker login → tag → push → pull 흐름과, digest(내용의 지문)와 tag(옮길 수 있는 이름표)의 차이를 확인합니다.

헷갈리기 쉬운 부분

공용 서버에서 docker login했다면 반드시 docker logout을 해야 합니다. credsStore가 없는 리눅스 서버에서는 인증 정보가 암호화가 아니라 base64 인코딩으로만 저장되기 때문입니다.

Docker Compose

여러 컨테이너를 파일 한 장으로 · docker run 옵션이 그대로 항목이 됨
▸

핵심 요지

컨테이너가 세 개만 되어도 docker run을 여러 번 순서 맞춰 쳐야 합니다. Compose는 이걸 파일 한 장으로 옮기는 도구입니다. 만들어지는 결과는 손으로 하는 것과 동일합니다.

docker run 옵션 → compose.yaml 항목 매핑

docker run 옵션compose.yaml 항목
--name webservices: 아래의 서비스 이름
-p 8088:80ports:
-e KEY=VALUEenvironment:
-v 이름:/경로volumes: (이름은 맨 아래 volumes:에 선언)
--network ...따로 안 써도 됨. compose가 프로젝트 전용 네트워크를 자동 생성
(순서는 사람이 맞춤)depends_on: + healthcheck:

서비스 기동 순서 (healthcheck 기준)

1stdb (Healthy)
→
2ndapp
→
3rdweb (외부 노출)
depends_on은 준비 완료 보장이 아님

단순 depends_on은 컨테이너 시작 순서만 제어합니다. DB가 실제 요청을 받을 준비까지 기다리려면 DB에 healthcheck를 정의하고 의존 서비스에서 condition: service_healthy를 사용해야 합니다. 애플리케이션 자체의 재시도 로직도 함께 두는 것이 안전합니다.

compose.yaml 뼈대

services:
  web:
    image: nginx:alpine
    ports: ["8088:80"]
    depends_on: [app]
  app:
    build: ./app
    environment:
      DB_HOST: db          # 서비스 이름이 곧 호스트 이름
    depends_on:
      db:
        condition: service_healthy
  db:
    image: mariadb:10.11
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect"]
volumes:
  db-data:

이름으로 서로 찾는다

compose는 프로젝트 전용 네트워크를 만들고, 서비스 이름을 호스트 이름으로 그대로 씁니다. 그래서 앱 코드에 IP를 적을 필요 없이 DB_HOST: db만 쓰면 됩니다. (5장 bridge 네트워크와 동일한 원리)

주요 명령

명령하는 일
docker compose up -d네트워크·볼륨·컨테이너 생성. 준비 완료 대기는 condition: service_healthy를 명시한 의존 관계에만 적용
docker compose ps / logs / exec컨테이너 ID 대신 서비스 이름으로 다룸
docker compose up -d --scale app=3같은 서비스를 여러 벌 띄움
docker compose down컨테이너·네트워크만 삭제, 볼륨은 남음
docker compose down -v볼륨까지 삭제 (init.sql이 다시 실행됨)
복습 포인트

2일차 마무리 집중실습 6 (3tier · 무중단 · 롤링 · 라이브 투표)이 이 장을 기반으로 진행됩니다. compose.yaml과 쿠버네티스 매니페스트는 적는 내용(이미지, 포트, 환경변수, 볼륨, 개수)이 거의 같다는 점을 기억해두면 쿠버네티스로 넘어갈 때 유리합니다.

헷갈리기 쉬운 부분

down과 down -v의 차이를 놓치면 실습 중 데이터가 갑자기 사라진 것처럼 보일 수 있습니다. down은 볼륨을 남기고, down -v는 볼륨까지 지웁니다. (2장의 익명 볼륨 이야기와 본질적으로 같은 주제입니다.)

헬스체크와 CI/CD

실행에서 끝내지 않고 상태 확인과 배포 흐름까지 연결
▸

헬스체크는 무엇을 확인하는가

/healthz 같은 엔드포인트는 비즈니스 기능이 아니라 프로세스의 생존 여부와 요청을 받을 준비 상태를 확인하는 진단용 API입니다. Docker의 HEALTHCHECK, 로드밸런서, 이후 학습할 Kubernetes probe가 이 신호를 사용합니다.

개념확인하는 것실패했을 때 판단
liveness프로세스가 죽거나 멈췄는가재시작이 필요한 상태

헷갈리기 쉬운 부분

HTTP 200만 반환하는 형식적인 검사보다 목적에 맞는 내부 상태를 확인해야 합니다. 다만 liveness에서 외부 DB 장애까지 검사하면 앱 자체가 정상이어도 재시작이 반복될 수 있으므로, 살아 있음과 준비됨을 분리해야 합니다.

Git push → CI build/test → Docker image build → Registry push
→ 배포 설정의 image tag/digest 변경 → pull → rolling update

Docker는 애플리케이션을 어디서든 같은 방식으로 실행할 수 있는 이미지로 패키징하는 구간을 담당합니다. 운영에서는 latest만 사용하기보다 검증한 버전 태그나 digest를 남겨 어떤 이미지가 배포됐는지 추적할 수 있어야 합니다.

다음 진도와의 경계

서비스가 한두 개라면 한 서버에 Docker와 Compose만 사용해도 충분할 수 있습니다. Kubernetes는 컨테이너 수가 많아져 복구·확장·업데이트를 사람이 직접 관리하기 어려워질 때 필요합니다. 이어서 Kubernetes 복습 노트에서 선언형 관리와 Pod·Deployment·Service 흐름을 확인할 수 있습니다.

Cross-chapter

장을 넘나들며 자주 헷갈리는 포인트 총정리

이미지 vs 컨테이너

이미지는 틀(템플릿), 컨테이너는 그 틀로 찍어 낸 것(실행 중인 프로세스)입니다. 하나의 이미지로 여러 컨테이너를 띄울 수 있고, 컨테이너를 아무리 고쳐도 이미지 자체는 바뀌지 않습니다(Copy on Write).

익명 볼륨 vs 네임드 볼륨

익명 볼륨도 일반적인 컨테이너 삭제 후 남을 수 있지만 새 컨테이너가 자동으로 재사용하지 않아 데이터와 연결이 끊기기 쉽습니다. docker rm -v나 docker run --rm 조건에서는 함께 정리될 수 있습니다. 네임드 볼륨(-v 이름:/경로)은 다시 연결하기 쉬운 것이 핵심입니다.

EXPOSE vs docker run -p

EXPOSE는 Dockerfile에 적는 문서화용 표시일 뿐 실제로 포트를 열지 않습니다. 호스트와 컨테이너 사이에 실제로 길을 뚫는 것은 언제나 docker run -p 호스트포트:컨테이너포트입니다.

CMD vs ENTRYPOINT

ENTRYPOINT는 고정 명령(뒤에 인자가 붙음), CMD는 기본값(통째로 덮어써짐)입니다. 둘 다 있으면 ENTRYPOINT가 명령어, CMD는 그 명령어의 인자로 동작합니다. docker run 뒤에 준 인자는 항상 CMD 자리를 대신합니다.

COPY vs ADD

둘 다 파일을 이미지에 넣지만, ADD는 URL 다운로드와 압축 자동 해제까지 합니다. 특별한 이유가 없으면 동작이 예측 가능한 COPY를 씁니다.

namespace vs cgroup

namespace는 "무엇이 보이는가"(프로세스·네트워크·파일시스템 격리), cgroup은 "얼마나 쓸 수 있는가"(CPU·메모리 등 자원 제한)를 담당합니다. 자원 초과 시 커널의 OOM Killer가 개입하는 것은 cgroup 영역입니다.

docker run vs docker start

run은 새로 만들어서 띄우는 것, start는 이미 있는(멈춘) 컨테이너를 다시 켜는 것입니다. run을 반복하면 같은 이름 충돌 또는 컨테이너가 계속 쌓이는 문제가 생깁니다.

Docker vs containerd vs runc

셋은 경쟁 관계가 아니라 층이 다른 도구입니다. Docker(사람이 쓰는 CLI+데몬) → containerd(이미지·수명주기 관리, 쿠버네티스 기본 런타임) → runc(namespace/cgroup을 실제로 만드는 최하위 도구) 순서로 호출됩니다.

docker tag vs docker push

tag는 이미지를 복사하는 게 아니라 이름표를 하나 더 다는 것(IMAGE ID 동일)이고, push는 실제로 레지스트리에 레이어를 전송하는 동작입니다. tag만으로는 아무 데이터도 이동하지 않습니다.

docker compose down vs down -v

down은 컨테이너·네트워크만 지우고 볼륨은 남깁니다. down -v는 볼륨까지 지워서 데이터가 초기화됩니다(init.sql이 다시 실행됨).
