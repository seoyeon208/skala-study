01

LangChain은 무엇을 연결할까?

모델을 만드는 기술이 아니라, 모델을 서비스에 연결하는 도구
▸

LangChain은 프롬프트·모델·출력 처리·검색·도구를 연결해 LLM 애플리케이션을 만드는 프레임워크입니다. LLM 자체도, 벡터 DB도 아닙니다. 비유하면 모델은 문장을 만드는 엔진이고, LangChain은 입력부터 결과 처리까지 연결하는 배선입니다.

1사용자 입력
→
2프롬프트 구성
→
3모델 호출
→
4응답 검증
→
5서비스 결과
교수님 강조 · 9/18

먼저 해결할 문제를 정하고 기술을 고릅니다. 계산·권한 검사처럼 결과가 정확해야 하는 일은 코드로 처리하고, 자연어 해석·요약처럼 LLM이 잘하는 부분을 연결합니다. 특정 공급자만 쓴다면 전용 SDK도 좋은 선택입니다.

구성무엇을 담당하나?
langchain-core메시지, 프롬프트, 출력 파서, Runnable 등 공통 규약
langchaincreate_agent 등 애플리케이션·에이전트 구성
langchain-openai 등 통합 패키지각 공급자의 API와 LangChain 인터페이스를 연결
LangGraph상태·분기·반복·중단과 재개 등 실행 흐름 관리
LangSmith실행 경로 추적, 디버깅, 평가에 사용하는 별도 도구

init_chat_model()은 모델을 직접 학습시키지 않습니다. 공급자와 모델 이름을 해석해 대응하는 모델 객체를 만듭니다. 따라서 OpenAI를 쓴다면 API 키뿐 아니라 langchain-openai도 필요합니다.

헷갈림 방지

표준 인터페이스는 모델 교체에 따른 수정을 줄여줄 뿐, 모든 모델의 기능·가격·출력 형태까지 같게 만들지는 않습니다. 도구 호출, 구조화 출력, 이미지 입력, 지원 파라미터를 바꿀 때마다 확인합니다.

SystemMessage역할·말투·지침모르는 내용은 모른다고 답하세요.
HumanMessage사용자의 입력LCEL을 설명해줘.

실습 준비

아래는 LangChain 1.x 방식의 학습용 예제입니다. 예제 모델명은 교재의 gpt-4o-mini를 사용합니다. 계정에서 사용 가능한 모델인지 확인하고, 실행 환경에서 동작한 패키지 버전을 기록하세요. Colab에서는 설치 명령 앞에 %pip를 사용합니다.

python -m pip install "langchain>=1,<2" langchain-openai python-dotenv

작업 폴더의 .env에 키를 저장하고 .gitignore에 .env를 추가합니다. 키가 있는 셀 출력·화면 캡처도 공유하지 않습니다. 실제 키는 아래 예제 문자열 대신 본인의 환경에만 입력하세요.

OPENAI_API_KEY=본인의_API_키
OPENAI_MODEL=gpt-4o-mini
import os
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

load_dotenv()
if not os.getenv("OPENAI_API_KEY"):
    raise RuntimeError(".env의 OPENAI_API_KEY를 확인하세요.")

model = init_chat_model(
    os.getenv("OPENAI_MODEL", "gpt-4o-mini"),
    model_provider="openai",
)
prompt = ChatPromptTemplate.from_messages([
    ("system", "처음 배우는 사람에게 핵심과 짧은 예시로 설명하세요."),
    ("human", "{topic}을 설명해줘."),
])
parser = StrOutputParser()
chain = prompt | model | parser
print(chain.invoke({"topic": "LangChain"}))

이후 예제는 별도 안내가 없으면 이 셀의 model, prompt, parser, chain을 사용합니다. 모델을 호출하는 셀은 비용이 발생합니다. 이 정적 블로그 자체에서 API를 호출하지는 않습니다.

교수님 강조 · 실습에서 막힌 지점

템플릿의 {topic}과 입력 딕셔너리의 topic이 같아야 합니다. Colab 런타임이 초기화되면 설치·키 로딩·객체 생성부터 다시 실행합니다. 앞에서 만든 변수 이름을 다른 예제에 덮어쓰지 않도록 주의하세요.

temperature는 출력의 무작위성, top_p는 후보 토큰 확률의 범위를 조절하는 설정입니다. 지원 범위는 모델마다 다릅니다. 낮은 temperature도 사실 정확성이나 완전한 재현성을 보장하지 않습니다. 출력 토큰 제한은 답변 길이를 제한하지만 입력 토큰·반복 호출 비용까지 제한하는 전체 예산은 아닙니다.

03

Runnable과 LCEL: 데이터가 어떻게 흐를까?

invoke라는 이름은 같아도 각 단계가 하는 일은 다르다
▸
교수님 반복 강조 · 9/18, 9/21

왜 프롬프트·모델·파서를 모두 invoke()로 실행할 수 있을까요? 공통 인터페이스인 Runnable을 따르기 때문입니다. 실행 방법을 통일한 것이지, 각 컴포넌트의 내부 기능이 같은 것은 아닙니다.

1dict
{topic: …}
→
2ChatPromptValue
완성된 메시지
→
3AIMessage
모델 응답
→
4str
추출한 텍스트
단계invoke의 역할외부 LLM 호출?
prompt.invoke({...})변수를 채워 프롬프트 생성아니요
model.invoke(완성된 프롬프트)응답 생성API 모델이라면 예
parser.invoke(AIMessage)응답에서 텍스트 추출StrOutputParser는 아니요
chain.invoke({...})연결된 전체 단계를 실행체인 안의 모델 단계에서 호출

LCEL은 LangChain Expression Language의 약자입니다. A | B | C는 A의 출력을 B에, B의 출력을 C에 전달하는 선언식 표현입니다. 체인을 만드는 것과 실행하는 것은 다릅니다. chain = ...으로 조립한 뒤 invoke() 등으로 실행합니다.

# 아래는 같은 데이터 흐름을 단계별로 펼친 형태입니다.
formatted = prompt.invoke({"topic": "LangChain"})
response = model.invoke(formatted)
answer = parser.invoke(response)
print(answer)

# 실행 결과 문장 자체는 호출마다 달라질 수 있습니다.
# chain = prompt | model | parser
실행 방식입력과 출력언제 사용?
invoke / ainvoke입력 하나 → 최종 결과 하나단일 요청 / 비동기 요청
batch / abatch입력 여러 개 → 결과 목록서로 다른 문서나 질문을 같은 체인으로 처리
stream / astream입력 하나 → 결과 조각을 순차 전달긴 답변을 기다리지 않고 표시

교수님이 소스까지 따라간 이유

교재의 상속 관계를 압축하면 PromptTemplate → StringPromptTemplate → BasePromptTemplate → RunnableSerializable → Runnable입니다. 모든 상속 단계를 암기하기보다, 공통 실행 규약은 기반 클래스에 있고 실제 처리는 각 컴포넌트가 구현한다는 구조를 이해하면 됩니다. 문서의 “소스 보기”와 함수의 docstring을 함께 보면 설명과 실제 구현을 연결할 수 있습니다.

디버깅 기준

파이프가 입력 타입을 마법처럼 고쳐주지는 않습니다. 프롬프트가 딕셔너리를 기대하는지, 다음 단계가 문자열을 기대하는지 확인하세요. 오류가 나면 전체 체인을 반복 호출하지 말고 단계별 입력·출력을 먼저 봅니다.

04

순차·병렬·원본 유지

빠르게 만들기 전에 작업 사이의 의존성을 확인한다
▸
SEQUENCE원문 → 요약 → 요약문 번역

번역이 요약 결과를 기다려야 함

PARALLEL원문 → [요약 ∥ 키워드] → 결과 묶음

각 작업이 원문만으로 실행 가능

교수님 반복 강조 · 9/21

병렬 처리의 조건은 서로 의존하지 않는 작업이라는 점입니다. 같은 입력을 쓴다는 이유만으로 무조건 병렬화하지 말고, 다른 작업의 결과나 공유 상태 변경을 기다려야 하는지 확인합니다.

from langchain_core.runnables import (
    RunnableParallel, RunnablePassthrough, RunnableLambda,
)

summarize = (
    ChatPromptTemplate.from_template("다음 글의 핵심을 요약해줘: {text}")
    | model | parser
)
translate = (
    ChatPromptTemplate.from_template("이 요약문을 영어로 번역해줘: {summary}")
    | model | parser
)
keywords = (
    ChatPromptTemplate.from_template("다음 글의 핵심어 3개를 골라줘: {text}")
    | model | parser
)

# 요약 결과를 다음 프롬프트의 summary라는 키에 연결
sequential = RunnableParallel(summary=summarize) | translate

# 두 작업 모두 같은 {"text": ...}를 받아 독립적으로 실행
parallel = RunnableParallel(summary=summarize, keywords=keywords)

sample = {"text": "LCEL은 컴포넌트를 연결한다. Runnable은 실행 규약이다."}
print(sequential.invoke(sample))
print(parallel.invoke(sample))

병렬 결과는 {"summary": "...", "keywords": "..."} 형태입니다. 두 요청이 각각 3초·5초라면 이상적인 병렬 소요 시간은 약 5초에 부가 시간이 더해집니다. 호출 두 번의 비용은 그대로이며 동시 요청이 늘면 rate limit에 걸릴 수 있습니다.

batch와 Parallel은 무엇이 다를까?

summarize.batch([입력1, 입력2])는 같은 요약 작업에 여러 입력을 넣습니다. RunnableParallel은 같은 입력을 여러 갈래의 작업에 전달합니다.

원문을 잃지 않으려면

# 입력 딕셔너리의 text를 유지하면서 summary를 추가합니다.
with_original = RunnablePassthrough.assign(summary=summarize)
# with_original.invoke(sample)
# → {"text": 원문, "summary": 요약문}

# 일반 함수를 체인의 한 단계로 사용
uppercase = chain | RunnableLambda(str.upper)

RunnablePassthrough()는 입력을 그대로 넘기고, assign()은 딕셔너리 입력에 새 키를 더합니다. str.upper는 문자만 변환하며 LLM 호출을 추가하지 않습니다. 단순 함수를 연결하는 데 별도 클래스를 만들 필요는 없습니다.

분기와 전처리: 연결 위치가 결과를 바꾼다

고객 피드백 라우팅과 개인정보 마스킹
▸

수업에서는 피드백을 긍정·부정·중립·상담원 이관으로 분류하고 결과에 따라 다른 체인으로 보내는 예제를 다뤘습니다. 분류는 모델이 하더라도, 실제 경로 선택은 미리 정한 조건으로 제한할 수 있습니다.

1원본 피드백
→
2분류 결과 검증
→
3조건별 체인 선택
→
4응답 또는 이관 안내
# LLM 없이 분기 원리만 확인하는 예제
from langchain_core.runnables import RunnableBranch, RunnableLambda

router = RunnableBranch(
    (lambda x: x["label"] == "positive",
     RunnableLambda(lambda x: "감사 답변 경로")),
    (lambda x: x["label"] == "negative",
     RunnableLambda(lambda x: "문제 확인 경로")),
    (lambda x: x["label"] == "neutral",
     RunnableLambda(lambda x: "추가 질문 경로")),
    RunnableLambda(lambda x: "상담원 이관 경로"),
)
assert router.invoke({"label": "negative"}) == "문제 확인 경로"
assert router.invoke({"label": "unknown"}) == "상담원 이관 경로"

RunnableBranch는 위에서부터 조건을 검사해 처음 참인 경로 하나를 실행합니다. 마지막 항목은 어떤 조건에도 맞지 않을 때의 기본 경로입니다. 위 코드는 안내 문자열만 반환하며 실제 상담 티켓을 만들지는 않습니다. 실제 서비스에서는 원문도 함께 유지하고 분류값을 스키마로 검증하세요.

마스킹은 언제 해야 할까?

BEFORE MODEL입력 → 마스킹 → 모델

외부 전송 전 보호

AFTER MODEL입력 → 모델 → 마스킹

출력 보호. 입력은 이미 전송됨

import re
from langchain_core.runnables import RunnableLambda

def mask_phone(text: str) -> str:
    # 학습용: 국내 010 번호의 두 가지 표기만 처리합니다.
    return re.sub(r"(?<!\d)010-?\d{4}-?\d{4}(?!\d)",
                  "[전화번호]", text)

assert mask_phone("연락처 010-1234-5678") == "연락처 [전화번호]"
assert mask_phone("01012345678") == "[전화번호]"

protected = (
    RunnableLambda(lambda x: {"topic": mask_phone(x["topic"])})
    | prompt | model | parser
    | RunnableLambda(mask_phone)
)
수업 예제 보완

9/21 후처리 예제는 화면에서 번호가 가려지는 원리를 보여줍니다. 외부 전송까지 보호하려면 입력 단계에서도 처리해야 합니다. 이 정규식은 이메일·이름·다른 전화번호 형식 등을 잡지 못하므로 완전한 개인정보 필터가 아닙니다. 로그와 검색 문서도 별도로 점검해야 합니다.

from pydantic import BaseModel, Field

class Review(BaseModel):
    """입력 리뷰에 명시된 정보만 추출합니다."""
    title: str = Field(description="작품 제목")
    rating: int | None = Field(
        default=None, ge=1, le=5,
        description="명시된 1~5점 평점. 없으면 null",
    )
    summary: str = Field(description="입력에 근거한 한 줄 감상")

structured = model.with_structured_output(Review)
review = structured.invoke(
    "입력에 없는 내용을 추가하지 말고 추출해줘. "
    "리뷰: 인사이드 아웃은 감정 표현이 좋았다. 5점 만점에 4점."
)
print(review.title, review.rating, review.summary)

“김치찌개 레시피 알려줘” 다음에 “더 맵게 하려면?”이라고 물으면 앞선 대화가 필요합니다. 독립적인 모델 호출은 이전 호출을 자동으로 이어받지 않습니다. 메시지를 누적해 전달하거나 상태 저장 기능을 연결해야 합니다.

교수님 반복 강조 · 9/18

bind_tools()는 모델에게 도구를 소개합니다. 호출 결과의 tool_calls는 “어떤 도구에 어떤 인자를 넣을지”라는 요청이지 실행 완료 결과가 아닙니다. 직접 호출할 때는 실행 루프를 구현하고, create_agent()를 쓰면 에이전트 실행기가 그 연결을 맡습니다.

도구를 고르는 데 전달되는 것은 주로 도구 이름·설명(docstring)·입력 스키마입니다. 함수의 내부 소스 코드 전체를 모델이 자동으로 읽는다고 생각하면 안 됩니다. 명확한 이름·타입·설명이 중요한 이유입니다.

from langchain_core.tools import tool
from langchain.agents import create_agent

@tool
def add_numbers(a: int, b: int) -> int:
    """두 정수를 정확하게 더해 합계를 반환합니다."""
    return a + b

# 연결만 하고 모델에 질의: 아직 add_numbers 실행 결과가 아닙니다.
bound = model.bind_tools([add_numbers])
request = bound.invoke("add_numbers 도구로 12와 30을 더해줘.")
print(request.tool_calls)  # name, args, id 등을 확인
print(add_numbers.invoke({"a": 12, "b": 30}))  # 직접 실행: 42

# 모델 판단 → 도구 실행 → 결과 전달 루프를 에이전트에 맡기기
calculator = create_agent(
    model=model, tools=[add_numbers],
    system_prompt="덧셈 요청은 add_numbers 도구를 사용하세요.",
)
result = calculator.invoke(
    {"messages": [{"role": "user", "content": "12와 30의 합은?"}]},
    config={"recursion_limit": 10},
)
print(result["messages"][-1].content)

모델은 계산 답변을 생성할 수도 있지만 항상 정확하다고 보장하기 어렵습니다. 계산 도구를 쓰면 실제 연산을 코드로 수행할 수 있습니다. 위의 호출은 도구 사용을 요청하지만, 실제 선택 여부는 반환된 메시지로 확인해야 합니다.

구분다음 작업을 정하는 주체예시
Chain / Workflow개발자가 정한 순서·조건요약 → 번역
Agent정해진 도구·규칙 안에서 모델이 다음 행동 선택검색 필요 판단 → 도구 실행 → 결과 보고 재판단
Toolkit관련 도구들의 묶음SQL 테이블 목록 조회·스키마 조회·쿼리 실행
수업 예제 읽을 때 주의

교재의 “항상 맑음, 22도”를 반환하는 날씨 함수는 연결 구조를 보여주는 모의 도구입니다. 실제 날씨를 확인한 결과가 아닙니다. 실시간 답변에는 신뢰할 수 있는 외부 데이터와 조회 시점이 필요합니다.

무한 반복은 장애에 더해 API 비용도 발생시킵니다. 위의 recursion_limit은 그래프 단계 상한이지 정확한 금액 상한이 아닙니다. 별도로 요청 횟수·시간·토큰 예산을 두고 종료 조건과 실패 처리를 정합니다. DB 도구는 최소 권한으로, 결제·삭제·전송은 사용자 확인 후 실행하도록 설계합니다.

교수님이 길게 설명한 세 가지

  1. chunk_size와 overlap: 너무 작으면 문맥이 끊기고 너무 크면 불필요한 내용까지 검색됩니다. 겹침은 경계의 정보 손실을 줄이지만 저장·검색 중복이 늘어납니다.
  2. 검색 개수 k: 크면 항상 좋지 않습니다. 필요한 근거를 더 담을 수 있지만 관련 없는 문서·비용·지연도 증가합니다. 대표 질문으로 시험해 정합니다.
  3. 임베딩 일관성: 문서와 질문은 호환되는 같은 임베딩 체계로 비교해야 합니다. 모델을 바꾸면 기존 문서 재임베딩·재색인을 검토해야 합니다. 차원 수만 같다고 호환되는 것도 아닙니다.

# 별도 설치: python -m pip install gradio
# 2장의 model, prompt, parser, chain을 먼저 생성합니다.
import gradio as gr

def explain_topic(text: str) -> str:
    text = text.strip()
    if not text:
        return "설명할 주제를 입력해 주세요."
    if len(text) > 1000:
        return "주제를 1,000자 이내로 입력해 주세요."
    return chain.invoke({"topic": text})

처음에는 대표 질문 10개 정도로 시작합니다. 정상 질문뿐 아니라 빈 입력, 문서에 없는 질문, 틀린 분류, 긴 대화, 도구 실패도 넣습니다. 형식은 자동 검증하고 내용은 근거·관련성·누락을 기준으로 평가합니다. 자동 LLM 평가도 비용이 들고 틀릴 수 있으므로 사람의 표본 검토와 함께 사용합니다.

  • 관측: 어느 단계가 느리거나 실패했는지, 모델·프롬프트·검색 설정과 사용량을 기록합니다. 개인정보·키는 로그에서 제외합니다.
  • 재시도: 일시적 오류에 제한적으로 적용합니다. 결제·전송 같은 작업을 통째로 재실행하면 중복 실행될 수 있습니다.
  • Fallback: 대체 모델의 출력 스키마·데이터 전송 정책까지 맞아야 합니다.
  • 권한: Tool·DB·검색 자료는 최소 권한. 모델의 판단을 인증·인가로 사용하지 않습니다.
  • 격리: 생성 코드를 실행한다면 별도의 격리 환경에서 시간·CPU·메모리·네트워크를 제한합니다.

자주 헷갈리는 포인트

Model vs LangChain

모델은 답변을 생성하고 LangChain은 여러 실행 단계를 연결합니다.

PromptTemplate vs Prompt

템플릿은 빈칸이 있는 틀, 프롬프트는 값이 채워진 실제 입력입니다.

batch vs Parallel

batch는 같은 작업에 여러 입력, Parallel은 같은 입력에 여러 작업입니다.

Parser vs 사실 검증

문자열·JSON으로 바꾸거나 형식을 검사해도 내용이 참이라는 뜻은 아닙니다.

Memory vs 학습

대화 이력을 다시 제공하는 것과 모델 가중치를 바꾸는 것은 다릅니다.

Tool call vs Tool result

호출 요청은 AIMessage, 실행 결과는 ToolMessage입니다.

RAG vs Fine-tuning

RAG는 검색 문맥을 제공하고, Fine-tuning은 학습으로 모델 가중치를 조정합니다.

Gradio UI vs 서비스 운영

입출력 데모 화면과 인증·서버·비용 관리가 갖춰진 운영 서비스는 다릅니다.
