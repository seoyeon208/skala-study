01

제어 루프와 아키텍처

API Server를 중심으로 spec과 status의 차이를 계속 메운다
▸
ENTRYkubectl · Controller · SDK → kube-apiserver

모든 변경과 조회가 통과하는 유일한 진입점

CONTROL PLANEetcd · Scheduler · Controller Manager

상태 저장 · 노드 선택 · desired state 조정

WORKER NODEkubelet · runtime · kube-proxy · CNI · CSI

컨테이너 실행 · 네트워크 · 스토리지 연결

API Server는 모든 요청의 입구, etcd는 상태 저장소, Scheduler는 Node 선택, Controller는 원하는 상태 복구, kubelet은 실제 실행을 맡습니다.

꼭 기억

모든 변경은 API Server를 거칩니다. Controller는 spec(원하는 상태)과 status(현재 상태)의 차이를 계속 줄입니다.

02

Pod 생명주기와 진단

Phase·Condition·Container State를 섞지 않고 읽는다
▸
1 · PENDINGScheduler가 Node 선택
2 · PULL이미지 받기
3 · CREATE설정·볼륨 적용
4 · RUN프로세스 시작
5 · READY트래픽 수신 가능
증상가장 먼저 확인
Pendingdescribe pod의 Events: 자원·taint·PVC
ImagePullBackOff이미지명·태그·Registry 권한
CrashLoopBackOfflogs --previous와 종료 코드
Running, Not ReadyreadinessProbe와 EndpointSlice

Running은 프로세스가 떠 있다는 뜻이지 서비스 가능하다는 뜻이 아닙니다. Ready=True인 Pod만 Service의 정상 백엔드가 됩니다.

진단 순서

get으로 범위를 잡고 → describe의 상태·Events를 보고 → 해당 컨테이너의 logs를 확인합니다. 컨테이너가 아직 없으면 로그도 없습니다.

▸

04

무중단 배포

새 Pod 생성보다 Ready 전환과 트래픽 관찰이 중요
▸
RECREATE전부 내리고 교체

단순하지만 중단 발생

ROLLING조금씩 교체

maxSurge · maxUnavailable

BLUE / GREEN환경 단위 전환

빠른 전환과 롤백, 자원 2배

CANARY일부 트래픽 검증

지표 기반 확대·중단

무중단의 핵심은 새 Pod가 Ready가 된 뒤 트래픽을 받고, 기존 Pod는 처리 중인 요청을 끝낸 뒤 종료되는 것입니다. readinessProbe·preStop·grace period·충분한 replicas가 함께 필요합니다.

꼭 기억

카나리는 관측성이 없으면 의미가 없습니다. 오류율·지연·업무 지표를 보고 확대하거나 즉시 롤백합니다.

설정의미잘못 잡으면
requestsScheduler가 예약하는 양너무 크면 비용 낭비, 너무 작으면 과밀 배치
CPU limit실행 중 CPU 상한초과하면 throttling으로 느려짐

HPA의 CPU 사용률은 requests를 기준으로 계산합니다. 따라서 requests가 비현실적이면 확장 판단도 흔들립니다.

꼭 기억

Node 배치·HPA·비용이 모두 requests에서 시작합니다. 평균만 보지 말고 p95, 최대 사용량, OOM·throttling 기록으로 조정합니다.

06

Scheduling과 배치 제어

조건이 많아질수록 Pending 가능성도 함께 커진다
▸
목적기능
특정 Node를 선택nodeSelector · nodeAffinity
Pod를 AZ·Node에 분산topologySpread · podAntiAffinity
전용 Node에 아무나 못 들어오게 함taint · toleration
중요 구분

Affinity는 어디에 둘지, taint는 누구를 막을지 정합니다. toleration은 입장 허용일 뿐 배치를 보장하지 않습니다.

HPA가 늘리는 것은 Pod이고, Cluster Autoscaler·Karpenter가 늘리는 것은 Node입니다. Pod가 늘어도 자리가 없으면 Pending입니다.

▸

EKS VPC CNI는 Pod에 VPC 사설 IP를 줍니다. 따라서 서브넷 IP와 ENI/IP 한도가 Pod 확장의 실제 상한입니다.

연결 실패 진단

Pod 직접 접속 → EndpointSlice → Service의 port/targetPort → Ingress host/path → Load Balancer 순으로 한 단계씩 확인합니다. 이름으로만 실패하면 CoreDNS와 DNS 정책을 봅니다.

꼭 기억

Service마다 LoadBalancer를 만들면 비용이 커집니다. 여러 서비스를 Ingress 뒤에 모을 수 있지만 Ingress Controller가 실제로 설치되어 있어야 합니다.

08

스토리지와 상태

Pod 수명과 데이터를 분리하고 AZ·접근 모드를 맞춘다
▸
WORKLOAD CLAIMPod → PVC

용량 · accessMode · StorageClass 요청

CLUSTER OBJECTPV ← StorageClass

동적 Provisioning · reclaimPolicy · bindingMode

DRIVER / STORAGECSI → EBS 또는 EFS

실제 생성 · Attach · Mount

EBSEFS
특정 AZ의 블록 스토리지, 주로 RWO여러 Node가 공유 가능한 파일 시스템, RWX

Pod가 사라져도 PVC와 실제 데이터는 별개입니다. 새 Pod가 같은 데이터를 쓰려면 StorageClass·PV·PVC·accessMode가 맞아야 합니다.

꼭 기억

EBS는 AZ를 넘지 않습니다. PVC Pending·Multi-Attach·volume node affinity conflict가 나오면 AZ와 accessMode부터 확인합니다.

09

설정과 Secret

설정을 이미지에서 분리하고 변경 반영 방식까지 설계
▸
주입 방식변경 반영
환경 변수새 Pod를 띄워야 반영
볼륨 파일파일은 갱신될 수 있지만 앱이 다시 읽어야 함

Secret의 base64는 인코딩이지 암호화가 아닙니다. Git에 평문 비밀을 넣지 말고, 최소 RBAC와 외부 Secret 저장소를 함께 사용합니다.

꼭 기억

설정 파일이 바뀌어도 앱 동작이 자동으로 바뀐다고 가정하면 안 됩니다. 재시작이 필요한지, 앱이 reload를 지원하는지 확인합니다.

10

인증·권한·보안

누구인가, 무엇을 할 수 있는가, 어떤 Pod를 허용할 것인가
▸
IDENTITYIAM · Access Entry → Kubernetes user

인증: 누구인가

AUTHORIZATIONRole · ClusterRole · Binding

인가: 어떤 verb로 어떤 resource를 다루는가

WORKLOAD IDENTITYServiceAccount → Pod Identity / IRSA

Pod에 최소 AWS 권한

RUNTIME POLICYSecurityContext · PSS · Admission

root·privilege·filesystem·capability 제한

SUPPLY CHAIN정적 분석 · 이미지 Scan/서명 · 감사 로그

배포 전후 위험 탐지

RBAC는 Kubernetes API 권한, EKS Pod Identity·IRSA는 Pod의 AWS API 권한입니다. 둘은 서로 대신할 수 없습니다.

권한 오류 진단

kubectl auth can-i → ServiceAccount·RoleBinding → Pod Identity·IRSA → Admission 정책 순으로 어느 경계에서 막혔는지 찾습니다.

꼭 기억

root 금지, 권한 상승 차단, 읽기 전용 파일시스템, 최소 RBAC가 기본입니다. 처음부터 필요한 권한만 허용합니다.

GitOps는 Git의 선언 상태를 기준으로 클러스터를 반복 동기화하는 방식입니다. 직접 수정한 값은 다시 덮일 수 있으므로 변경은 PR로 남기고, 렌더링 결과와 동기화 상태를 확인합니다.

증상에서 시작하는 최소 진단 지도

안 뜬다       → get pod → describe pod Events
이미지 실패    → image/tag → Registry 권한 → DNS/egress
계속 재시작    → describe → logs --previous → 종료 코드
접속 불가      → Pod 직접 → EndpointSlice → Service → Ingress/LB
볼륨 대기      → describe pvc → StorageClass → AZ/accessMode
권한 거부      → auth can-i → SA/Binding → Pod Identity/IRSA → Admission
느리다         → p95/p99 지표 → Trace → 해당 시간대 로그

비용은 requests 예약률, Load Balancer 수, 사용하지 않는 EBS/PV, 로그 보관 기간부터 점검합니다.

꼭 기억

장애 해결 명령만 남기지 말고 증상·영향·원인·근거·조치·재발 방지를 기록합니다.

Review map

자주 헷갈리는 포인트

Running vs Ready

Running이어도 readiness가 실패하면 Service 트래픽을 받지 않습니다.

requests vs limits

requests는 배치 예약, limits는 실행 중 상한입니다.

HPA vs Node 확장

HPA는 Pod 수, Karpenter·Cluster Autoscaler는 Node 수를 늘립니다.

Service vs Ingress

Service는 안정적인 내부 접근점, Ingress는 외부 HTTP 경로 규칙입니다.

Secret vs 암호화

base64는 인코딩입니다. 별도 보호가 필요합니다.

RBAC vs IAM

RBAC는 Kubernetes 권한, IAM은 AWS 권한입니다.
