01

왜 Kubernetes인가

명령 모음이 아니라 원하는 상태를 유지하는 운영 시스템
▸

Docker 다음에 필요한 것

Docker는 애플리케이션을 이미지로 만들고 컨테이너로 실행합니다. 컨테이너가 수십·수백 개가 되면 어느 서버에 배치할지, 죽었을 때 누가 다시 띄울지, 업데이트 중 트래픽을 어떻게 유지할지를 사람이 직접 처리하기 어렵습니다. Kubernetes는 이 운영 문제를 자동화합니다.

운영 질문Kubernetes의 답
어디에 실행할까?Scheduler가 조건과 자원을 보고 Node를 선택
죽으면?Controller가 desired state와 비교해 다시 생성
주소가 바뀌면?Service가 안정적인 접근점 제공
업데이트는?Deployment가 점진 교체와 롤백 관리

선언형 관리와 조정 루프

Manifest(YAML)의 spec: "Pod 3개가 필요하다"
현재 status: "Pod 2개가 실행 중이다"
Controller: 차이 1개를 발견 → Pod 1개 생성 → 다시 관찰
  • Manifest: 원하는 상태를 적은 YAML 파일
  • Resource: API Server에 등록되어 클러스터가 관리하는 객체
  • spec: 사용자가 원하는 상태
  • status: 시스템이 관찰한 현재 상태
핵심

kubectl apply가 Pod를 직접 실행하는 것이 아닙니다. 원하는 상태를 API Server에 전달하면 여러 컴포넌트가 계속 비교하고 조정합니다. 이것이 reconciliation과 self-healing의 출발점입니다.

02

클러스터 아키텍처

Control Plane은 판단하고 Worker Node는 실행한다
▸

Control Plane

API Server
모든 요청의 입구. 인증·인가·검증 후 상태를 처리한다.
etcd
클러스터의 상태를 저장하는 분산 Key-Value 저장소. 백업이 곧 클러스터 상태 백업이다.
Scheduler
Node가 정해지지 않은 Pod를 보고 자원·제약조건에 맞는 Node를 선택한다.
Controller Manager
Replica·Node·Endpoint 등 현재 상태가 원하는 상태와 같아지도록 조정한다.
Cloud Controller
클라우드 Load Balancer·Node·Route 같은 외부 인프라와 연결한다.

Worker Node

  • kubelet: 자신의 Node에서 Pod가 정의대로 실행되는지 관리
  • container runtime: containerd·CRI-O 등이 이미지를 받고 컨테이너 실행
  • kube-proxy: Service 트래픽 전달 규칙 구성
  • CNI: Pod 네트워크와 IP, CSI: 스토리지 연결
EKS 책임 경계

AWS가 Control Plane의 가용성과 운영을 맡아도, 사용자는 Worker Node·Pod·네트워크·권한·배포 설정과 비용을 관리해야 합니다. Worker가 없어도 EKS Control Plane 비용은 발생하므로 만들고 잊어버리면 안 됩니다.

03

생성 요청의 여행

apply 한 번 뒤에서 누가 어떤 순서로 일하는가
▸

Deployment를 적용했을 때

  1. kubectl이 kubeconfig의 cluster·user·context를 읽고 API Server에 요청한다.
  2. API Server가 인증·인가·검증을 거쳐 desired state를 etcd에 저장한다.
  3. Deployment Controller가 ReplicaSet을, ReplicaSet Controller가 필요한 Pod를 만든다.
  4. Scheduler가 Pending Pod에 알맞은 Node를 배정한다.
  5. 해당 Node의 kubelet이 CNI로 네트워크를 준비하고 runtime에 컨테이너 실행을 요청한다.
  6. Probe가 통과해 Ready가 되면 Service Endpoint에 포함되어 트래픽을 받는다.

자주 겪는 상황

Deployment가 관리하는 Pod 하나를 직접 삭제하면 Controller가 부족한 개수를 발견해 다시 만듭니다. 서비스를 멈추려면 Pod를 반복 삭제하지 말고 kubectl scale deployment NAME --replicas=0 또는 Deployment 삭제를 사용합니다.

kubectl과 장애 확인

▸

안전한 적용 흐름

kubectl config current-context
kubectl config set-context --current --namespace=my-app
kubectl diff -f app.yaml
kubectl apply --dry-run=server -f app.yaml
kubectl apply -f app.yaml

문제 확인 순서

kubectl get pods -o wide
kubectl describe pod POD_NAME       # 맨 아래 Events 확인
kubectl logs POD_NAME
kubectl logs POD_NAME --previous    # 재시작 전 컨테이너 로그
kubectl get events --sort-by=.lastTimestamp
  • Pending: 스케줄링·자원·PVC·IP 부족 가능성
  • ImagePullBackOff: 이미지 이름·태그·Registry 인증 확인
  • CrashLoopBackOff: 애플리케이션 종료 원인과 이전 로그 확인
  • Running이지만 0/1 Ready: readiness probe·의존성 확인
유용한 보조 명령

kubectl explain deployment.spec.template.spec로 필드를 확인하고, kubectl auth can-i create deployments로 현재 권한을 확인합니다. k 별칭은 입력을 줄일 뿐 동작은 같습니다.

05

Pod 생명주기

가장 작은 배포 단위이지만 직접 관리하는 단위는 아니다
▸

Pod 안에서 공유되는 것

Pod는 같은 Node에서 함께 실행되는 하나 이상의 컨테이너 묶음입니다. 컨테이너들은 네트워크 namespace와 IP를 공유하므로 localhost로 통신하고, 선언한 Volume도 함께 사용할 수 있습니다.

패턴역할
Init Container앱 시작 전에 설정·마이그레이션·의존성 확인. 성공해야 앱 컨테이너가 시작
Sidecar로그 수집·프록시처럼 앱을 보조하며 함께 실행
Ambassador/Adapter외부 통신 대리 또는 데이터 형식 변환
Init Container 주의

Pod가 다시 생성되면 Init Container도 다시 실행됩니다. 파일이 이미 있거나 마이그레이션 일부가 수행된 상태에서도 안전하도록 멱등성(idempotency)을 가져야 합니다.

종료 흐름

Pod 삭제 시 Endpoint에서 제외되고 SIGTERM이 전달된 뒤 terminationGracePeriodSeconds 동안 정상 종료를 기다립니다. 애플리케이션이 종료 신호를 처리하고 새 요청을 받지 않게 해야 배포 중 요청 손실을 줄일 수 있습니다.

06

Deployment와 롤아웃

ReplicaSet을 통해 Pod 개수와 버전을 관리
▸

왜 Pod를 직접 만들지 않는가

Pod는 교체 가능한 실행 단위입니다. Deployment는 새 버전마다 ReplicaSet을 만들고, ReplicaSet은 지정된 수의 Pod를 유지합니다. 운영에서는 Pod보다 Deployment의 replicas와 Pod template을 변경합니다.

kubectl set image deployment/app app=registry/app:1.2.0
kubectl rollout status deployment/app
kubectl rollout history deployment/app
kubectl rollout undo deployment/app
kubectl scale deployment/app --replicas=3
RollingUpdate 옵션의미
maxSurge기존 replicas보다 추가로 만들 수 있는 최대 Pod 수
maxUnavailable업데이트 중 사용할 수 없어도 되는 최대 Pod 수
minReadySecondsReady 후 안정 상태로 인정하기까지 기다리는 시간
롤백이 가능한 이유

이전 ReplicaSet 정보가 남아 있기 때문입니다. 단, 이미지 태그를 계속 덮어쓰는 latest보다 버전 태그나 digest를 써야 어떤 버전으로 돌아가는지 추적할 수 있습니다.

07

Probe와 리소스

Running·Ready·Healthy를 구분하고 스케줄링 기준을 제공
▸
검사질문실패 시
startupProbe초기 구동이 끝났는가?성공할 때까지 다른 probe 시작을 미룸
readinessProbe지금 요청을 받을 수 있는가?Service Endpoint에서 제외
livenessProbe프로세스를 재시작해야 하는가?컨테이너 재시작
무조건 세 개가 정답은 아님

잘못된 liveness는 일시적인 DB 장애에도 정상 프로세스를 계속 재시작시킬 수 있습니다. 느린 시작에는 startup, 트래픽 제어에는 readiness를 먼저 정확히 설계하고, liveness는 재시작으로 회복되는 고장만 검사합니다. 거짓 재시작 위험이 크면 liveness를 생략하는 판단도 가능합니다.

requests와 limits

필드누가 사용하는가의미
requestsScheduler배치 판단에 사용하는 보장 요청량
limitsruntime·kernel컨테이너가 사용할 수 있는 상한
resources:
  requests:
    cpu: 250m       # 0.25 CPU
    memory: 256Mi   # 이진 단위
  limits:
    cpu: "1"
    memory: 512Mi

CPU 초과는 보통 throttling, 메모리 limit 초과는 OOMKilled로 이어질 수 있습니다. 250m는 250밀리코어이며, 메모리의 Mi와 CPU의 m을 혼동하지 않습니다.

08

Service와 Ingress

변하는 Pod 앞에 안정적인 주소와 HTTP 라우팅을 둔다
▸

Service가 Pod를 찾는 방법

Pod는 재생성될 때 이름과 IP가 달라집니다. Service는 selector와 일치하는 label을 가진 Ready Pod들을 Endpoint로 묶고, 고정된 ClusterIP와 DNS 이름을 제공합니다.

selector:
  app: api        # Service

metadata:
  labels:
    app: api      # Pod template: 정확히 일치해야 함
Service 유형용도
ClusterIP클러스터 내부 통신의 기본
NodePort각 Node의 포트로 노출, 주로 제한적 실습·구성 요소 연결
LoadBalancer클라우드 외부 LB를 생성해 공개
ExternalName외부 DNS 이름을 내부 Service처럼 참조

Ingress의 역할

Ingress는 host/path → Service HTTP(S) 라우팅 규칙이고, 실제 트래픽을 처리하는 Ingress Controller가 별도로 있어야 합니다. 규칙만 만들고 Controller가 없으면 동작하지 않습니다.

비용 관점

Service마다 LoadBalancer를 만들면 외부 LB 비용이 늘어납니다. 여러 서비스의 도메인·경로 라우팅을 하나의 Ingress 계층에서 공유할 수 있습니다. 관리형 ALB와 NGINX Ingress는 운영 편의·기능·비용이 다르므로 환경에 맞춰 선택합니다.

09

DNS·CNI·요청 흐름

이름 해석, Pod IP 할당, 패킷 전달을 분리해서 이해
▸

내부 통신

애플리케이션은 Pod IP를 하드코딩하지 않고 service-name.namespace.svc.cluster.local 같은 Service DNS를 사용합니다. CoreDNS가 이름을 ClusterIP로 해석하고, kube-proxy 규칙이 Endpoint Pod로 전달합니다.

CNI와 IP 계획

CNI는 Pod 네트워크를 구성합니다. EKS의 VPC CNI에서는 Pod가 VPC 대역의 IP를 사용하므로 subnet의 사용 가능한 IP가 부족하면 Node CPU·메모리가 남아도 Pod가 Pending에 머물 수 있습니다.

port-forward의 경계

kubectl port-forward pod/POD 8080:8080은 내 PC와 특정 리소스 사이에 임시 통로를 여는 디버깅 도구입니다. 운영 사용자를 위한 노출 방식은 Service·Ingress이며, 터미널이 끊기면 port-forward도 끝납니다.

10

ConfigMap과 Secret

이미지와 환경별 설정을 분리하는 12-Factor 원칙
▸

개발·운영마다 다른 URL이나 옵션을 이미지에 굽지 않고 외부 설정으로 주입하면 같은 이미지를 여러 환경에서 사용할 수 있습니다. 값 하나는 환경변수로, 설정 파일은 Volume으로 마운트할 수 있습니다.

리소스담는 것주의
ConfigMap일반 설정, 파일 내용비밀값을 넣지 않음
Secret비밀번호·토큰·인증서기본 저장은 base64 표현이며 암호화와 다름
보안 핵심

base64는 누구나 복원할 수 있는 인코딩입니다. RBAC 최소 권한, etcd encryption at rest, 외부 Secret Manager, 로그·Git 노출 방지를 함께 설계해야 합니다. Manifest에 실제 비밀값을 커밋하지 않습니다.

환경변수로 주입한 값은 Pod 재시작 전까지 자동 갱신되지 않습니다. Volume 파일은 갱신될 수 있어도 애플리케이션이 다시 읽는지는 별도 문제이므로, 변경 반영 방식까지 정해야 합니다.

11

PV·PVC와 상태 저장

Pod 수명과 데이터 수명을 분리하고 접근 모드를 확인
▸
PVC
사용자가 필요한 용량·접근 모드를 요청
StorageClass
어떤 provisioner와 정책으로 볼륨을 만들지 정의
PV
클러스터가 관리하는 실제 스토리지 자원
CSI
클라우드·스토리지 제품을 Kubernetes와 연결하는 표준 인터페이스
접근 모드뜻
ReadWriteOnce (RWO)한 Node에서 읽기·쓰기
ReadOnlyMany (ROX)여러 Node에서 읽기 전용
ReadWriteMany (RWX)여러 Node에서 읽기·쓰기, 지원 스토리지 필요

데이터베이스처럼 각 인스턴스에 안정적인 이름과 개별 볼륨이 필요하면 StatefulSet을 검토합니다. 하지만 Kubernetes 안에 DB를 올리는 것이 항상 최선은 아닙니다. 백업·복구·복제 운영 부담까지 비교해 클라우드 관리형 DB가 더 적합할 수 있습니다.

삭제 정책 확인

PVC나 클러스터를 지웠을 때 실제 볼륨이 남는지는 StorageClass의 reclaim policy에 따라 달라집니다. Delete와 Retain을 확인하지 않고 정리하면 비용이 남거나 데이터가 삭제될 수 있습니다.

12

배포 전략·보안·비용

무중단은 하나의 기능이 아니라 여러 조건의 조합
▸
전략방식장단점
Rolling Update기존 Pod를 새 Pod로 점진 교체기본 기능으로 간단하지만 두 버전이 잠시 공존
Blue-Green구·신 환경을 모두 준비하고 트래픽 전환빠른 전환·복구, 자원 비용 큼
Canary일부 트래픽만 신버전에 보내 지표 확인위험을 작게 검증, 라우팅·관측 필요

세 전략은 서로 배타적인 이름표가 아닙니다. Rolling으로 Pod를 교체하면서 일부 트래픽만 Canary에 보내거나, Blue-Green 환경 안에서 점진 전환하는 식으로 조합할 수 있습니다.

운영 Manifest가 길어지는 이유

  • securityContext로 non-root, capability, read-only filesystem 등을 제한
  • requests/limits, probe, graceful shutdown으로 장애와 배포 안정성 확보
  • PodDisruptionBudget·anti-affinity·topology spread로 동시 장애 범위 축소
  • NetworkPolicy와 RBAC로 통신·API 권한을 최소화
Cloud 습관

실습을 마치면 Deployment만이 아니라 LoadBalancer, EKS cluster, Node group, PVC/PV, EBS 같은 과금 자원을 확인합니다. 편의 기능을 만드는 순간 비용과 보안 책임도 함께 생깁니다.

Common traps

헷갈리는 포인트 총정리

비슷해 보이지만 역할이 다른 개념을 마지막으로 구분합니다.

Running ≠ Ready

프로세스가 실행 중이어도 readiness가 실패하면 Service 트래픽을 받지 않습니다.

Service ≠ Ingress

Service는 Pod 집합의 안정적인 접근점, Ingress는 HTTP(S) host/path를 Service로 보내는 규칙입니다.

Ingress ≠ Ingress Controller

Ingress는 선언한 규칙이고 Controller는 그 규칙을 읽어 실제 프록시·LB를 구성하는 실행 주체입니다.

requests ≠ limits

requests는 배치 판단 기준, limits는 실행 중 사용 상한입니다.

Secret의 base64 ≠ 암호화

base64는 표현 방식일 뿐 보안 기능이 아닙니다. 권한·저장 암호화·외부 비밀 관리가 필요합니다.

CNI ≠ CSI

CNI는 네트워크와 Pod IP, CSI는 스토리지 연결을 담당합니다.
