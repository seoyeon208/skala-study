01

클라우드와 탄력성

서버 구매가 아니라 필요할 때 자원을 빌리고 되돌리는 운영 방식
▸
관점온프레미스클라우드
비용장비를 미리 구매하는 CapEx 중심사용량 기반 OpEx, 다만 방치하면 계속 과금
용량최대 수요를 예측해 선구매수요에 맞춰 확장·축소
속도조달·설치에 시간이 필요분 단위로 자원 생성 가능
운영시설·하드웨어까지 직접 관리서비스에 따라 AWS와 책임을 나눔

Elastic과 Scalable의 차이

Scalability는 더 큰 부하를 감당할 수 있는 능력이고, Elasticity는 실제 수요에 맞춰 자원이 늘고 줄어드는 성질입니다. 클라우드의 핵심은 큰 서버가 아니라 필요한 만큼 빠르게 조정하고 사용한 만큼 지불하는 것입니다.

비용 함정

종량제는 자동 절약이 아닙니다. 사용하지 않는 인스턴스·디스크·공인 IPv4·스냅샷도 자원별 과금 규칙에 따라 비용이 생길 수 있으므로 생성과 삭제를 한 쌍으로 관리합니다.

03

Region·AZ·Multi-AZ

지리적 범위와 장애 격리 단위를 구분해 배치
▸
Geographic areaRegion · ap-northeast-2

데이터 위치 · 서비스 제공 여부 · 지연 · 가격을 고려해 선택

Failure isolationAZ A ↔ AZ B ↔ AZ C

독립 전력·네트워크를 갖춘 물리적으로 분리된 장애 격리 단위

Physical facilitiesData centers

컴퓨팅·스토리지·네트워크 장비가 실제로 위치

Region은 국가와 같은 말이 아닙니다. AWS가 정의한 별도의 지리적 영역이며 한 국가에 여러 Region이 있을 수도 있습니다. 2026년 공식 문서 기준 각 Region은 최소 3개의 AZ를 제공하지만, 전체 Region·AZ 수는 계속 변하므로 암기보다 구조를 이해합니다.

Multi-AZ가 필요한 이유

한 AZ 장애가 전체 서비스 장애로 번지지 않도록 애플리케이션과 데이터를 여러 AZ에 분산합니다. 단, 서버를 두 개 만든 것만으로는 부족합니다. 요청 분산, 상태 복제, 자동 장애 조치, 복구 시험이 함께 있어야 합니다.

RDS 예시

Multi-AZ 구성은 다른 AZ에 대기 복제본을 두고 장애 시 전환해 가용성을 높입니다. 읽기 확장을 위한 Read Replica와 목적이 다릅니다.

SECURITY IN THE CLOUD고객

데이터 · IAM · 암호화 선택 · 서비스 설정 · 앱

책임 경계는 서비스에 따라 달라집니다. EC2에서는 고객이 게스트 OS 패치, 애플리케이션, 보안 그룹 설정을 담당합니다. S3·DynamoDB처럼 더 추상화된 서비스에서도 데이터 분류, 접근 권한, 암호화 옵션 설정은 고객 책임입니다.

Identity
루트 사용자는 계정·결제 등 꼭 필요한 경우로 제한하고 MFA 활성화
Permission
IAM 사용자·역할에는 업무에 필요한 최소 권한만 부여
Secret
Access Key와 Secret Key를 코드·저장소·이미지에 넣지 않음
Exposure
노출되면 즉시 비활성화·삭제하고 새 키 발급, 로그와 비용 확인
GitHub 사고 예방

.env를 .gitignore에 넣는 것만으로 이미 커밋된 비밀은 사라지지 않습니다. 비밀이 한 번이라도 공개 저장소에 올라갔다면 삭제 커밋만 하지 말고 먼저 키를 폐기·교체해야 합니다. 가능하면 장기 Access Key 대신 IAM Role과 임시 자격 증명을 사용합니다.

여섯 원칙은 서로 독립된 점수가 아닙니다. 예를 들어 Multi-AZ는 안정성을 높이지만 비용도 늘 수 있습니다. 요구사항과 위험을 먼저 정하고 왜 그 균형을 선택했는지 기록하는 것이 리뷰의 핵심입니다.

헷갈림 교정

“지속 가능성”은 단순한 지속적 개선이 아니라 워크로드의 에너지·자원 효율을 높여 환경 영향을 줄이는 관점입니다. 지속적인 운영 개선은 주로 운영 우수성과 연결됩니다.

IP 주소의 변화

기본 공인 IPv4는 인스턴스를 중지하면 반환되고 다시 시작할 때 새 주소를 받습니다. 기본 네트워크 인터페이스의 사설 IPv4는 중지·시작 후에도 유지됩니다. 고정 공인 주소가 필요하면 Elastic IP 같은 방법을 검토하되 공인 IPv4 자체에도 비용이 생길 수 있습니다.

2026년 9월 기준 AWS Free Tier

신규 고객은 가입 시 100달러 크레딧을 받고 활동으로 최대 100달러를 추가 획득할 수 있습니다. Free plan은 최대 6개월 또는 크레딧 소진 시까지이며 일부 서비스만 사용할 수 있습니다. 기존 계정과 Paid plan의 조건은 다를 수 있으므로 강의의 750시간 예시를 그대로 가정하지 말고 생성 직전 Billing·Free Tier 화면과 해당 서비스 가격을 확인합니다.

종료와 삭제는 다르다

EC2를 중지해도 연결된 EBS·스냅샷·Elastic IP 등은 남을 수 있습니다. 실습 후 인스턴스 상태만 보지 말고 각 리소스와 Billing 대시보드, 예산 알림까지 확인합니다.

정적 파일은 S3 같은 Origin에 두고 CloudFront로 전송 지연을 줄일 수 있습니다. 동적 API와 데이터베이스는 주 사용자가 가까운 Region에 배치하고, 가용성 요구가 높다면 여러 AZ에 분산합니다. 모든 리소스는 IaC로 만들고, 운영 접근은 IAM Role과 MFA를 사용하며, 예산 알림과 로그를 함께 구성합니다.

Region은 AWS의 지리적 영역입니다. 국가 경계와 항상 일치하지 않습니다.

AZ vs 데이터센터

AZ는 장애 격리 단위이며 하나 이상의 물리 데이터센터로 구성될 수 있습니다.

Multi-AZ vs Backup

Multi-AZ는 가용성, Backup은 시점 복구가 중심입니다. 서로 대체하지 않습니다.

CloudFront vs Local Zone

CloudFront는 콘텐츠 전송·캐시, Local Zone은 선택한 컴퓨팅·스토리지를 사용자 가까이 둡니다.

Outposts vs Direct Connect

Outposts는 AWS 장비를 현장에 두고, Direct Connect는 현장과 AWS를 전용 연결합니다.

CDK vs CloudFormation

CDK는 CloudFormation의 대체 엔진이 아니라 코드를 Template으로 변환해 배포하는 작성 방식입니다.

AWS 책임 vs 고객 책임

AWS가 모든 보안을 대신하지 않습니다. 데이터·권한·설정은 계속 고객 책임입니다.

무료 한도 vs 무료 보장

계정·시점·서비스별 조건이 다릅니다. 항상 현재 Billing과 가격표를 확인합니다.
